---
title: "x402 Agent Integration"
description: "Make automated Canton Coin payments from an agent or backend service using the x402 client SDK."
---

An **agent** (or payer) is any client that calls x402-gated endpoints. When the server returns `402 Payment Required`, the agent creates a `TransferCommand` on the Canton ledger, attaches the payment proof, and retries — all without manual intervention.

## Install

```bash
npm i @canton-network/x402-canton-client
```

## Onboarding

Before making payments, the agent needs a Canton party with an Ed25519 signing key. `ensureWallet` handles key generation, party allocation, and persistence. On subsequent runs it restores from the saved key.

```typescript
import { ensureWallet } from "@canton-network/x402-canton-client";

const wallet = await ensureWallet({
  relayUrl:  "https://<your-facilitator>",
  network:   "canton:mainnet",
  partyHint: "my-agent",
});

console.log(wallet.party); // "my-agent::1220..."
```

To restore an existing key (e.g. after re-deploying):

```typescript
const wallet = await ensureWallet({
  relayUrl:  "https://<your-facilitator>",
  network:   "canton:mainnet",
  key:       existingKeyMaterial,
  restore:   true,             // skip re-allocation; party already on-ledger
});
```

## Balance

```typescript
import { RelayClient } from "@canton-network/x402-canton-client";

const relay = new RelayClient({ relayUrl: "https://<your-facilitator>" });
const balance = await relay.balance(wallet.party);

console.log(balance.cc);       // "12.3400000000"  — human-readable CC
console.log(balance.amulet);   // 12.34            — numeric
console.log(balance.holdings); // [{ cid, amount }, ...]
```

## Making Payments

`makePayingFetch` returns a drop-in `fetch` replacement. It intercepts `402 Payment Required`, creates a `TransferCommand` on-ledger, and retries the request automatically.

```typescript
import { makePayingFetch } from "@canton-network/x402-canton-client";

const payFetch = await makePayingFetch({
  relayUrl:  "https://<your-facilitator>",
  network:   "canton:mainnet",
  partyHint: "my-agent",
});

const res = await payFetch("https://api.example.com/resource");
const data = await res.json();
```

### Read payment metadata from the response

```typescript
import { readPaymentResponseHeader } from "@canton-network/x402-canton-client";

const res = await payFetch("https://api.example.com/resource");
const payment = readPaymentResponseHeader(res);
// { transaction: "<updateId>", network: "canton:mainnet", ... }
```

### Advanced options

```typescript
const payFetch = await makePayingFetch({
  relayUrl:  "https://<your-facilitator>",
  network:   "canton:mainnet",
  partyHint: "my-agent",
  // restrict which Canton networks to pay on
  networkFilter: (n) => n === "canton:mainnet",
  // retries on transient 402s (default 4)
  maxPaymentRetries: 4,
});
```

## Withdraw

Send CC to any Canton party — for topping up a sub-agent, moving funds to a wallet, or collecting earnings.

```typescript
import { withdraw } from "@canton-network/x402-canton-client";

// Send a specific amount
const result = await withdraw({
  to:     "recipient::1220...",
  amount: "5.0000000000",      // Daml Decimal string, 10 decimal places
});
console.log(result.updateId);  // Canton ledger updateId of the transfer
console.log(result.amount);    // amount actually sent

// Send full balance
const result = await withdraw({ to: "recipient::1220..." });
```

## Pending Incoming Transfers

Check for CC transfers incoming to the agent's party that are not yet claimed:

```typescript
const relay = new RelayClient({ relayUrl: "https://<your-facilitator>" });
const pending = await relay.pending(wallet.party);

for (const tx of pending.pending) {
  console.log(tx.cid, tx.amount, tx.sender);
}
```

## Facilitator Discovery

```typescript
const relay = new RelayClient({ relayUrl: "https://<your-facilitator>" });
const info = await relay.supported();
// { kinds: [{ scheme: "exact-canton", network: "canton:mainnet" }], ... }
```

## How TransferCommand Creation Works

When `payFetch` intercepts a 402, it exercises `ExternalPartyAmuletRules_CreateTransferCommand` on the Canton ledger using interactive submission:

1. `POST /v2/interactive-submission/prepare` → gets `preparedTransactionHash`
2. Agent signs the hash with its Ed25519 key
3. `POST /v2/interactive-submission/execute` with the signature
4. Agent resolves the `transferCommandCid` from the create `updateId`
5. Retries the original request with `PAYMENT-SIGNATURE: <base64 PaymentPayload>`

The Canton ledger atomically moves CC from sender to receiver and archives the `TransferCommand` in a single transaction.

## Nonce Management

Each `TransferCommand` must include a strictly increasing nonce. The SDK reads `nextNonce` from the sender's `TransferCommandCounter` on SV Scan before each payment. Reusing a nonce causes the facilitator to reject with `invalid_exact_canton_nonce_reuse`.

## First-Request Latency

The first payment after a cold start is slower than subsequent ones. SV Scan caches `AmuletRules` (5 min TTL) and `OpenMiningRound` (30 s TTL) — these caches are empty on startup, so the first request warms them. Subsequent payments typically complete in 10–25 seconds on Canton mainnet.
